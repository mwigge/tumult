# demo-app — the fault-injection target

A small orders API over Postgres, instrumented with OpenTelemetry. It's the
service Tumult disrupts in the [one-command demo](../README.md): every fault
domain (network latency, DB connection kills, container pause, CPU/memory
stress, process signals, SSH, agentic) ultimately shows up as a change in this
app's traces and metrics in SigNoz.

It is deliberately tiny and boring on the happy path — the interesting behavior
is what it does **under fault**.

## Design goal: degrade, never crash

The whole point is to stay up and keep emitting telemetry while its
dependencies are attacked:

- Database unreachable (paused container, killed connections, network latency)
  → `/health` flips to **503**, data endpoints return **5xx** JSON, and the
  handler span is marked with an **error status**. The process does not exit.
- DB operations are bounded by a **2s timeout** (`DB_OP_TIMEOUT`) and the health
  ping by **900ms** (`HEALTH_PING_TIMEOUT`), so a paused/partitioned database
  surfaces as a fast 5xx rather than a hung request — which is what makes the
  fault visible on the dashboards instead of just stalling.
- Schema bootstrap **retries forever** with capped backoff, so the app can start
  before Postgres is ready (the compose stack comes up in parallel).

## HTTP surface

| Method & path | Purpose | Under DB fault |
|---|---|---|
| `GET /health` | `200 {"status":"ok"}` when the DB is reachable. Tumult probes this; the compose healthcheck hits it. | `503 {"status":"unavailable"}` |
| `GET /orders` | List orders (DB read). | `503 {"error":"..."}` |
| `POST /orders` | Insert a randomly generated order (DB write). | `503` |
| `GET /orders/{id}` | Fetch one order; `404` if absent. | `503` |
| `GET /checkout/{id}` | The showcase multi-step trace (see below). | `503` (step 1 fails) |

## Trace structure

Every handler is its own span (`GET /health`, `GET /orders`, …), exported as an
OTel span to the collector with `service.name = demo-app`.

`GET /checkout/{id}` is the richest trace — a parent span with three children so
it has visible depth in SigNoz:

```
GET /checkout/:id
├── db query          (loads the order; nested db.get_order span)
├── inventory check   (simulated downstream reservation, ~15–45ms)
└── payment           (simulated payment authorization, ~25–60ms)
```

Under a DB fault, `db query` errors and the parent span carries the error
status — a clear before/after in the trace waterfall when you inject latency or
pause Postgres.

## Configuration (env only)

Defaults match the demo [CONTRACT](../CONTRACT.md); everything is overridable.

| Var | Default | Meaning |
|---|---|---|
| `DATABASE_URL` | `postgres://demo:demo@demo-postgres:5432/orders` | Postgres connection |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://tumult-collector:4318` | OTLP HTTP traces endpoint |
| `LISTEN_ADDR` | `0.0.0.0:8080` | HTTP bind address |
| `RUST_LOG` | `info` | tracing/log filter |

Baseline traffic is **not** generated by this binary — the separate
[`demo-traffic`](../traffic) service drives a steady request mix so there's
always load to disrupt.

## Running standalone (without the full stack)

Useful for developing the app or reproducing a fault behavior in isolation:

```bash
# 1. A throwaway Postgres
docker run --rm -d --name demo-pg -p 5432:5432 \
  -e POSTGRES_DB=orders -e POSTGRES_USER=demo -e POSTGRES_PASSWORD=demo \
  postgres:16-alpine

# 2. The app, pointed at it (no collector → traces just no-op export)
cd demo/app
DATABASE_URL=postgres://demo:demo@localhost:5432/orders \
LISTEN_ADDR=127.0.0.1:8080 \
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 \
cargo run

# 3. Exercise it
curl -s localhost:8080/health           # {"status":"ok"}
curl -s -XPOST localhost:8080/orders    # 201 + the new order
curl -s localhost:8080/orders           # the list
curl -s localhost:8080/checkout/1       # the multi-step trace

# 4. Simulate a DB fault and watch it degrade (not crash)
docker pause demo-pg
curl -si localhost:8080/health          # 503 {"status":"unavailable"}
docker unpause demo-pg
curl -s localhost:8080/health           # back to 200
```

## Build & test

Self-contained crate (its own `[workspace]`, excluded from the root Tumult
workspace so it doesn't bloat the main build):

```bash
cd demo/app
cargo build
cargo test          # handler + fault-path tests using an in-memory store stub
cargo clippy --all-targets -- -D warnings
```

## Source map

- `src/main.rs` — startup: env config, schema bootstrap (retry loop), graceful shutdown.
- `src/app.rs` — router, handlers, span wiring, JSON error mapping, timeouts.
- `src/db.rs` — `OrderStore` trait + `PgStore` (Postgres), `record_span_error`.
- `src/telemetry.rs` — OTLP exporter + tracing subscriber setup.

## Container

Built by `docker/Dockerfile.demo-app` (multi-stage, slim runtime, `EXPOSE 8080`).
In the demo it depends on `demo-postgres` being healthy and exports traces to
`tumult-collector`.
