THE FIELD GUIDE

Turn a fault into understanding.

A useful experiment ends with an explanation you can defend. Follow this process with any of the four lessons. No AI key required.

The processFault mechanismsReading resultsGo deeper

01 / ASK, OBSERVE, EXPLAIN

One question. Three measured phases.

  1. Predict before you click.

    Read the hypothesis: every sampled request succeeds and p95 latency stays at or below 200 ms. Predict whether this fault will cause slow responses, errors, or both. Write down what would contradict your prediction.

  2. Establish the baseline.

    Tumult measures eight requests before applying the fault. If the service is already failing or slow, resolve that first. You cannot attribute an existing problem to a fault you have not injected.

  3. Change one behavior.

    Acknowledge the sandbox scope and run the lesson. The real Tumult executor enables the selected behavior in the bundled teaching API, then measures responses while it is active. Your question to the tutor never starts an experiment.

  4. Verify recovery.

    Compare the recovery samples with baseline after cleanup. Stop experiment requests cancellation and cleanup; a target-enforced lease also bounds fault lifetime. No recovery samples means that run has not demonstrated recovery.

  5. Reflect on the evidence.

    Explain what changed, whether your prediction held, and what remains unknown. Export the result before proposing the next experiment. A weakness discovered is useful evidence.

02 / KNOW WHAT YOU ARE CHANGING

Four mechanisms, four different questions.

Slow responses

Mechanism: adds 400 ms of application delay before responding.

Look for: a latency objective breaking even when requests succeed.

Ask: would your monitoring notice a service that is available but too slow to use?

HTTP failures

Mechanism: returns HTTP 503 while the fault is active.

Look for: fast responses that are nevertheless failures.

Ask: how could a latency-only dashboard make this outage appear healthy?

Unavailable cache

Mechanism: application code simulates an unavailable cache and fails the request.

Look for: dependency failure becoming a user-visible failure.

Ask: should the endpoint return a stale value, fetch an uncached result, or fail explicitly?

Database timeout

Mechanism: waits 600 ms, then returns HTTP 503.

Look for: latency and availability degrading together.

Ask: which deadline should expire first: the dependency timeout or the whole request budget?

The responses are real. The dependencies are simulated.

There is no Redis or PostgreSQL server to stop in these lessons. An application delay is not kernel packet loss or retransmission. These measurements teach the mechanism in this sandbox; they do not certify a production network or database.

03 / READ THE RESULT HONESTLY

Execution success and resilience are different questions.

The native Tumult journal records the generated experiment's activities, rollback, and steady-state checks. It can report Completed when the method finishes and the post-fault state recovers.

The lab verdict compares the measured fault window with baseline and recovery:

Deviated
Baseline and recovery met the objective, but the injected fault broke it. The experiment exposed a weakness.
Held
The available phase measurements satisfied the objective in this run. This is bounded evidence, not a general guarantee.
Inconclusive
The intended comparison was not established, for example because baseline or recovery failed or execution stopped.

A completed native journal and a deviated lab result can therefore both be correct. The executor did its job; the service failed the objective during injection.

Eight samples are a demonstration, not a production SLO.

Each phase samples eight sequential requests. The nearest-rank p95 calculation is ceil(8 × 0.95) = 8, so the displayed p95 is the largest observed latency in that phase. One failure is 12.5% of this sample; it is not a reliable estimate of production availability.

Use these observations to understand a controlled change. Representative workload, longer measurement windows, and repeated independent runs are needed before drawing broader conclusions. Host load and scheduling can affect every measured value.

Keep three pieces of evidence together.

  • Experiment definition: the generated .toon plan explains what Tumult was asked to do.
  • Export evidence: JSON contains the lab's measured phases, raw samples, events, and verdict.
  • Tumult journal: the native .toon execution record shows what the executor recorded, when available.

The download links appear with run results. See the Tumult experiment-format reference for native fields.

04 / MAKE THE NEXT EXPERIMENT USEFUL

Turn the observation into a better question.

Write a conclusion with your actual numbers: “Fault-window latency exceeded 200 ms while all requests succeeded. Recovery returned below the threshold. This supports a latency failure caused by the simulated application delay; it does not establish how real network delay would affect retries.”

The lab provides fixed lessons. The following are development exercises for a separate copy of the teaching target, not switches already built into this interface:

  • Cache fallback: can requests succeed without the cache, and what happens to freshness or downstream work?
  • Bounded retries: can transient failures recover inside the request budget without amplifying load or duplicating work?
  • Timeout budgets: can the dependency stop consuming time before the overall request deadline expires?
  • Circuit breakers: can repeated failures avoid repeated expensive calls, and how does recovery probing work?
  • Concurrency limits: can one slow dependency avoid occupying all available workers?

Add tests for a chosen change, rerun the same lesson, and compare evidence. To study a real dependency or network fault, use a separate disposable environment containing that dependency and define its own bounded experiment.
